# CI timing audit, 2026-10-21

Why verification and release runs took so long, what changed, and the measured
result. Every number is from a GitHub Actions run of `ponchione/scrapeyard`
(Ubuntu 24.04 hosted runners, 4 CPUs) unless it says *local* or *estimate*.

## Before: what the runs measured

All successful runs from 2026-10-15 to 2026-10-21 (run → job → step timings
from the Actions API):

| Workflow | Runs | Wall time, median (range) | Runner minutes, median |
| --- | --- | --- | --- |
| Release artifact and deployment rehearsal | 9 | 35.1 min (33.3–38.5) | 35.0 |
| CI | 23 | 16.5 min (9.6–20.2) | 23.6 |
| Recovery, restore, load, and soak qualification | 10 | 10.0 min (9.1–23.9) | 9.9 |
| Container and browser smoke | 9 | 4.2 min (3.5–5.1) | 4.2 |
| Container security and SBOM | 23 | 3.9 min (3.4–5.2) | 3.8 |
| Dependency audit | 26 | 0.7 min (0.6–0.9) | 1.2 |

Queue time was never a factor: the longest wait for a runner was 19 s.

### CI: the test suite ran on one CPU

In run 39617188141 (push of `7bccba5`), `Quality / Python 3.12` took 704 s and
`Quality / Python 3.14` took 671 s. Of that, pytest took 655 s and 617 s
(3,254 and 3,258 tests). Installing dependencies took 8–14 s, because the
Poetry and pip download caches hit their primary key in every job. Caching
was not the problem. The suite ran serially on a 4-CPU runner. One 300 s
stretch came from `tests/unit/test_egress_policy_installer.py`, whose tests
start hundreds of shim processes each.

### Release rehearsal: two releases built one after the other

In run 39617277107 (the dispatched release of `7bccba5` over `ae5bb5e`), the
single job took 2,059 s:

| Step | Seconds |
| --- | --- |
| Build, scan and qualify the previous release | 697 |
| Build, scan and qualify the candidate release | 579 |
| Deploy, refuse, roll back, boot-service rehearsal | 700 |
| Everything else (runtime install, pack, upload) | ~80 |

Each `release_artifact.py create` spends about 455 s in the quick
qualification profile. Those phases are fixed by design: recovery about 153 s,
soak 136 s, load 59 s, Redis restart 43 s, admission 31 s, and backup/restore
19 s. The rest goes to the image build (78 s the first time, layers reused the
second) and the scans (about 100 s). The two releases are independent, but the
lane ran them back to back, so 1,276 s sat on the critical path twice over.

### Scans: the Trivy database was downloaded once per image

`scripts/run_container_security_scan.sh` gave each `trivy image` container its
own throwaway cache. Every scan therefore downloaded the 130 MiB vulnerability
database again: three times per scan run, six times per release rehearsal.

### Images built more than once (not changed)

On a pull request that touches the runtime, the production image is built
independently by the container security, container smoke, qualification and
release workflows (twice in the last, once per release). The builds take
79–139 s each, from `--pull` or `--no-cache`. That is deliberate: every lane
proves the image builds from pinned inputs on a clean host, and the scan sees
what a fresh build would ship. Sharing one image through a registry or
artifact would save at most about 2 minutes per lane and would weaken that
proof, so it was left alone.

### The 2026-10-21 rehearsal failure, from its log

The earlier diagnosis blamed Playwright DNS. The log of run 39601139356 shows
otherwise. `getaddrinfo ENOTFOUND playwright.download.prss.microsoft.com`
appears, but each download then succeeded from `cdn.playwright.dev`
("Chromium 136.0.7103.25 … downloaded to /ms-playwright/chromium-1169"). The
step failed later, in `run_container_security_scan.sh`, with exit code 1 from
Trivy's vulnerability gate, after Trivy started its Python-package check. The
image of that previous revision had installed `certifi==2026.2.25`. The fix
went out as certifi 2026.10.19 (PYSEC-2026-4320).

## Changes

1. **CI runs the suite over all runner CPUs.** `pytest-xdist` 3.8.0 is a
   development dependency. The quality legs run
   `pytest -n auto --dist worksteal`. The tests, the `-W error` setting and
   the 80% coverage floor are unchanged; coverage is combined across workers.
   Work stealing stops the slow egress-installer file from leaving one
   worker busy after the others finish. `--durations=25` now lists the
   slowest tests in each log.
2. **Two tests that parallel load exposed were fixed, not skipped.**
   - `test_browser_budget_retains_limiter_until_cancellation_acknowledged`
     gave its run budget 10 ms on the real clock. On a busy worker the
     deadline passed before the fetch started, so the cancellation the test
     waits for never came (CI run 39626413094). The budget now uses a stopped
     clock. Checked locally: with a 50 ms delay injected, the test passes
     with the fix and fails without it.
   - `test_policy_replacement_restores_prior_deny_path_at_every_mutation_stage`
     runs the installer twelve times. It takes 22 s alone, and beside other
     workers it hit the 60 s default timeout (CI run 39628439590). It now has
     a 180 s timeout. In the verified runs it took 36–60 s.
3. **The release rehearsal builds both releases at the same time.**
   `release-rehearsal.yml` now has three jobs:
   - `revisions` picks the candidate and the previous revision, as before.
   - A two-way `release` matrix runs `release_artifact.py create` for each
     revision on its own clean runner, then packs the release with root as
     the owner of every file and hands it on as a one-day artifact.
   - `release-rehearsal` runs on a third runner that built neither release.
     It checks both archives' SHA-256, unpacks them, runs
     `release_artifact.py verify` on each, and then runs the unchanged
     `run_deployment_rehearsal.sh --boot-service`. The archive it extracts as
     an operator would, `verify --scanned`, and uploads on dispatch is the
     same byte stream it rehearsed.

   Every image the rehearsal deploys is loaded from a release archive, as on
   the production host, so the lane now also proves that the archives carry
   all of their images.
4. **One Trivy database per scan run.** The scan script creates one Docker
   volume for the run, mounts it as Trivy's cache for every image scan and
   the configuration scan, and removes it on exit. All images in a run are
   judged against the same database snapshot. Nothing persists between runs,
   so no scan can use a stale database.

## After: verified runs

| Measure | Before | After | Source |
| --- | --- | --- | --- |
| CI quality leg, 3.12 | 704 s (pytest 655 s) | 307 s and 311 s (pytest 266 s, 271 s) | runs 39617188141 → 39629514413, 39629517927 |
| CI quality leg, 3.14 | 671 s (pytest 617 s) | 212 s and 255 s (pytest 162 s, 206 s) | same |
| CI wall time | 11.8 min (that push) | about 5.2 min | same |
| CI runner minutes | about 24.5 | about 10.2 | sum of job durations |
| Coverage, 3.12 / 3.14 | 90.37% / 90.73% | 90.39% / 90.74% | job logs |
| Release rehearsal wall time | 35.1 min median (2,059 s in 39617277107) | 28.4 min | PR run 39626412977 |
| Release rehearsal runner minutes | about 35 | about 40.8 (5 + 809 + 751 + 882 s) | same |
| Trivy database downloads per scan run | 3 | 1 | candidate job of 39626412977; its previous-revision job ran the old script and still downloaded 3 |
| Local full suite (4 workers) | 346 s serial | 97 s | *local*, WSL2, 24 CPUs |

The release lane's new critical path is revisions (5 s), the slower release
(809 s), and the rehearsal (882 s). Inside the rehearsal, receiving the two
archives of about 1.3 GB each took 111 s and checking and unpacking them took
18 s; that is the price of the hand-over. The deployment rehearsal itself
took 713 s, as before (700 s).

The scan change saved about 13 s per scan run (39 s against 52 s for the same
three scans in the two release jobs of 39626412977). That is small, but it
also removes two chances per run for a mirror outage to fail the gate.

The container security, smoke, qualification and dependency audit
workflows were unchanged apart from the scan script. On the PR they took
205 s, 197 s, 578 s and 34–44 s, within their earlier ranges.

## Tradeoffs and what is left

- **The rehearsal costs more runner minutes than before:** about 41 against
  35, from a third runner and the artifact hand-over. It saves about 7
  minutes of wall time. The repository is public, so hosted minutes are not
  billed.
- **Each release now builds on a runner with no other layers.** Before, the
  candidate reused the previous release's layers. Wall time is what improved;
  per-release build time did not.
- **The quick qualification profile, about 7.5 minutes per release, is now
  the floor of the release lane,** together with the 12-minute deployment
  rehearsal. Both are fixed recovery, soak and rollback checks; shortening
  them would mean checking less.
- **The egress-installer tests are the slowest in CI** (17–60 s each beside
  other workers), because each runs real shell scripts against process shims.
  If the 3.12 leg grows again, they are where to look first, using the
  `--durations` list in its log.
- `actionlint` (latest image) reports no findings for the changed workflows.
